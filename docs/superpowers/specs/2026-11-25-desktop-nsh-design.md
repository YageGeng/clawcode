# Desktop 客户端迁移到 NSH 设计

日期：2026-11-25。状态：修订待审阅（第二次修订：加入 relay 远程控制；功能范围改为「大方向一致」；界面参考 ChatGPT 桌面应用；经过一轮自查修正）。

本文把桌面客户端从 gpui-kit（原 `crates/desktop`，Rust）迁移到 Native Shell（NSH），并从一开始就把经 relay 的远程控制纳入架构。客户端界面用 TSX 编写，桌面端通过 Rust 扩展在进程内运行 clawcode 后端，并经 iroh 与其他设备互连。工作在 worktree 分支 `feat/desktop-nsh` 上进行，从 `feat/desktop-client`（`0d8b404`）分出。

## 1. 背景与目标

产品是原生的桌面客户端。原来基于 gpui-kit 的客户端是一次失败的尝试，已在 N0 删除；WebUI 只用于前期调试，以后删除，新客户端不迁就它。

目标：

- **原生控件与平台一致性**：用各平台自己的视图渲染，打字、滚动、输入法、无障碍的表现与系统一致。
- **远程控制**：一台设备上的桌面 App 能经 relay 控制另一台设备上运行的 clawcode。每个桌面 App 同时是主机（在本机运行 agent）和遥控器（控制别的主机）。这一能力从第一阶段开始设计和交付，不是事后补的接口。
- **多端**：同一个 NSH 应用以后能出移动端（作为遥控器）、TUI 等版本。

功能范围：大方向与旧客户端的里程碑 M1–M4c 一致（会话与对话、交互与控件、工作区面板、轨迹、消息操作、Provider 登录与设置），细节不要求逐项一致。旧的 spec 与计划已从仓库删除，需要参考时从 git 历史取（`0d8b404` 的 `docs/superpowers/specs/2026-11-*-desktop-*`、`plans/2026-11-*-desktop-*`、`crates/desktop/`）。每个里程碑在自己的计划里写明本次要做的功能与验收项。

成功标准：

- 本地：在 Linux 上完成上述各功能方向的日常使用流程；macOS、Windows 可以构建。
- 远程：两台设备（或同一台机器上的两个实例）用配对码配对后，遥控器能完成一次完整的远程对话、审批权限请求、查看改动；主机撤销设备后对方立即断开。

## 2. 已确认的决策

| # | 决策 |
| --- | --- |
| 1 | 客户端用 NSH 的「TSX + Rust 扩展」模式：界面与客户端逻辑写 TSX，Rust 负责后端、远程连接与配对 |
| 2 | 就地替换：`crates/desktop` 与 gpui-kit 依赖已在 N0 删除；旧实现从 git 历史取 |
| 3 | 功能范围与旧客户端大方向一致，不要求细节一致 |
| 4 | ACP 跑在 `AcpTransport` 接口上：本机用原生通道（`NativeTransport`），远程主机用 `RelayTransport`；上层连接与状态代码不区分两者 |
| 5 | 客户端逻辑归桌面应用所有（`apps/desktop/src/client`），不与 WebUI 共用 |
| 6 | 远程连接用 iroh（1.5）：按设备公钥拨号，QUIC 打洞直连，打不通时经 relay 转发；端到端加密由 iroh 的 QUIC/TLS 提供。开发阶段用 n0 的公共 relay（官方定位为开发与测试用、限流）；正式发布前另行决定用自建 `iroh-relay` 还是 Iroh Services，relay 地址始终可配置 |
| 7 | 每个桌面 App 既是主机也是遥控器；主机只在桌面 App 运行时可被远程控制 |
| 8 | 配对：配对码（桌面之间复制粘贴；主机同时显示二维码，留给以后的移动端扫码），无账号、无云服务；主机确认后把对方公钥加入「已信任设备」，可随时撤销 |
| 9 | 已信任设备拥有与本地相同的权限；只属于主机的能力（远程配对管理、Provider 登录与凭据）在 ACP 层对远程连接拒绝 |
| 10 | 远程逻辑放在新 crate `crates/remote`，`ext/backend` 只做薄包装；以后无界面的 `app` 也能复用 |
| 11 | 不用 A2UI 构建客户端本身 |
| 12 | 遵循 NSH 设计规范与编码规范：先建设计系统与 `ui` 层，页面只用 `ui` 组件，每个页面先写动效清单 |
| 13 | WebUI（`web/`）只作调试用，保持原样不改，以后整体删除 |
| 14 | 客户端只经 ACP 访问主机上的数据（会话、工作区文件、改动、git 状态），不直接读主机的文件系统；附件从遥控器自己的磁盘读取后作为内容上传。这样本机与远程主机走同一条路径 |

## 3. 架构与目录

```text

┌──────────── 桌面 App ────────────┐            ┌──────── 桌面 App ────────┐
│ TSX: AppStore                    │            │ TSX: AppStore            │
│  ├ 本机   ─ NativeTransport ──┐  │            │  └ 远程主机 ─ RelayTransport
│  └ 远程主机 ─ RelayTransport  │  │            │          │               │
│ ext/backend (Rust)           │  │            │ ext/backend (Rust)       │
│  ├ BackendThread ◄───────────┘  │            │  └ RemoteClient ─────────┼──┐
│  │   └ Application + Kernel      │            └──────────────────────────┘  │
│  │        ▲ serve_lines（每条连接一个）                                       │
│  └ RemoteHost（iroh 端点）◄──── iroh：P2P 直连，打不通时经 relay ─────────────┘
└──────────────────────────────────┘
（右侧设备同样有自己的本机后端与 RemoteHost，图中略去。）
```

```text
crates/remote/            远程控制（Rust，根 workspace 成员）
  identity                设备密钥（iroh 密钥，持久化在数据目录），设备名
  host                    RemoteHost：接收连接、配对握手、信任检查，每条连接交给 serve_lines
  client                  RemoteClient：连接已配对的主机，收发 ACP 帧
  pairing                 配对码（主机公钥、relay 地址、一次性密钥、有效期）的编码与校验
  trust                   TrustStore：已信任设备的增删查、撤销
crates/acp/               AcpServerFactory::serve_lines；新增 AcpTransportKind::Remote 与主机专属能力的拒绝
apps/desktop/             NSH 应用（产品）
  nsh.json, App.tsx, DESIGN.md, FEASIBILITY.md
  src/client/             客户端逻辑，不依赖界面：
    transport.ts            AcpTransport 接口
    acp/                    ACP 协议、JSON-RPC 请求与通知
    domain/, workspace/     领域模型、会话状态、更新解码、路由
    trajectory/, changes/   （以后）轨迹模型、改动树、PatchLoader 等
  src/transport/          NativeTransport（本机）、RelayTransport（远程主机）
  src/ui/                 设计系统：token、动效、图标、基础控件
  src/gallery/            组件展示页
  src/stores/             signal store
  src/<功能>/             shell、sidebar、session、composer、panel、details、trajectory、settings、remote 等
  ext/backend/            Rust 扩展（nshm crate，根 workspace 成员）：
                          Backend（本机后端）、RemoteHosting（主机侧远程开关与配对）、
                          RemoteConnection（遥控器侧连接，形态同 Backend）
web/                      调试用 WebUI，不改动，以后删除
```

- `src/client` 起点是 WebUI 中不依赖 React、zustand、浏览器的协议与状态代码，此后独立演进；桌面端在 N1 写自己的 controller，可参考 WebUI 的逻辑。
- 旧 Rust 客户端里 WebUI 没有的逻辑（transcript 分组与折叠、轨迹模型与时间轴、改动树、`PatchLoader`、消息标记、按轮次改动筛选）在用到它的里程碑里用 TS 移植进 `src/client`，相应的 Rust 单元测试改写成 TS 测试。
- `ext/backend` 链接 `app`、`acp`、`remote`，持有一个共享的后台 tokio 运行时。本机后端（Application 与 Kernel）、`RemoteHost`、`RemoteClient` 都跑在它上面，但彼此独立：本机后端启动失败时，仍能作为遥控器去控制别的主机。`RemoteHost` 只在本机后端运行时接收连接，每条已认证的连接调用一次 `AcpServerFactory::serve_lines`，与本机连接共享同一个 Kernel。
- Kernel 支持多条 ACP 连接同时在线（HTTP 传输已是每条连接一个组件），本机与远程可以同时查看、操作同一个会话，并各自收到更新。

## 4. 远程控制

### 4.1 身份与连接

- 每个安装有一把设备密钥（iroh 密钥），首次启动生成，存在桌面应用自己的数据目录（`$XDG_DATA_HOME/clawcode-desktop/` 一类的平台目录，与后端配置无关；文件只允许当前用户读写）。设备名默认取主机名，可在设置里改。
- 应用的数据目录可以用环境变量指定，用于同一台机器上运行两个实例（测试）或分开的配置。
- 同一把密钥既用于作为主机被连接，也用于作为遥控器去连接。
- 连接使用自己的 ALPN，带协议版本（如 `clawcode/acp/1`）。版本不匹配时连接失败，界面提示「双方版本不兼容，请升级」。一条 iroh 连接上开一个双向流，流上按行传 ACP JSON-RPC 帧，与 `serve_lines` 的帧格式一致。
- relay 与地址查找：开发阶段用 iroh 的 N0 预设（n0 公共 relay 与其地址查找服务）；同时开启局域网发现，同一局域网内不经 relay。配对码里带着主机的 relay 地址，遥控器保存下来，即使地址查找不可用也能经该 relay 找到主机。relay 地址可配置为自建 `iroh-relay`；正式发布前决定 relay 与地址查找的托管方式。

### 4.2 配对

1. 主机在设置中打开「允许远程控制」，`RemoteHost` 开始接收连接。
2. 主机点「添加设备」，显示一串可复制的配对码与对应的二维码。配对码包含主机公钥、relay 地址、一次性密钥（至少 128 位随机数），5 分钟内有效，用一次即失效；连续几次提交错误的密钥后该配对码作废。
3. 遥控器（桌面）粘贴配对码，连接主机，在配对握手里提交一次性密钥与自己的设备名。以后的移动端扫同一个二维码。
4. 主机校验密钥后弹窗确认：「允许 “设备名” 控制这台电脑？它将能在这台电脑上收发对话、运行命令、读写工作区文件。」允许后对方公钥写入已信任设备；拒绝或超时则断开。
5. 遥控器把主机（公钥、名称、relay 地址）存入自己的「远程主机」列表；以后按公钥自动重连，不需要再配对。

### 4.3 授权与安全

- iroh 的 QUIC/TLS 认证双方公钥；relay 只转发密文。
- `RemoteHost` 在交给 ACP 之前检查对方公钥是否在已信任设备里；不在且不是有效的配对握手时立即关闭连接。
- 已信任设备的 ACP 连接以 `AcpTransportKind::Remote` 运行，权限与本地相同，但以下能力在 ACP 层拒绝（返回明确的错误，界面上相应入口不显示）：
  - 远程控制的配对与信任管理；
  - Provider 登录、写入或读取凭据。
- 撤销设备：从已信任设备中删除，并立即关闭它的在线连接。
- 主机界面常驻显示远程连接状态（「N 台设备正在远程连接」），可以一键查看与断开。
- 日志遵循 AGENTS.md 规则 13：记录连接、配对、撤销等生命周期事件与设备公钥的短指纹，不记录配对码、一次性密钥与帧内容。

### 4.4 遥控器界面

- `AppStore` 管理多个主机：「本机」加上已配对的远程主机。每个主机有自己的连接状态、会话目录和会话状态。侧栏顶部的主机切换决定侧栏显示哪台主机的工作区与会话；新会话的输入框上下文条也能选主机（见 5.1），在别的主机上发出新会话后，侧栏随之切到那台主机。
- 远程主机断开时界面显示离线与重试，不影响本机和其他主机。
- 远程主机上的会话与本机会话使用同一套界面；只属于主机的入口（Provider 登录、远程配对管理）在远程主机上不显示。

## 5. 设计系统与 `ui` 层

### 5.1 视觉与布局方向

整体参考 ChatGPT 桌面应用（Codex）的界面：布局、层次与交互模式，不用它的 logo、图标与品牌元素，也不做我们没有的功能（语音、云端环境、插件）。参考截图只留在本机（`.superpowers/ref/`，git 忽略）。

- **观感**：应用底色接近白，主区纯白，几乎不用边框；层次靠留白、字号与灰度（次要文字约 50% 透明度的前景色）。暗色版同样思路。
- **字号**：对话正文 15pt、行高约 1.6；界面文字 14pt；元信息 13pt。
- **圆角与阴影**：输入框卡片约 22pt；菜单、弹层约 16pt；侧栏选中行为圆角胶囊；阴影只用一圈很淡的描边加轻微投影。
- **外壳**：标题栏只放侧栏开关与前进、后退（N1 验证 NSH 能否自定义 Linux 标题栏；不能时用系统标题栏，这几个按钮放到侧栏顶部）；不做左侧图标栏，设置入口在侧栏底部。没有顶部的会话标签页，会话从侧栏切换；标签页只用于右侧面板。
- **侧栏**：顶部主机切换（「本机 ▾」，下拉列出已配对的远程主机）；「新会话」；「工作区」按目录分组，展开显示该目录的会话；「最近」。行约 32pt，悬停时行尾出现置顶、归档；运行中、等待处理等状态用行尾小标记。
- **会话视图**：
  - 顶栏：工作区图标与标题，右侧「更多」与面板开关。
  - transcript 居中一列，最宽约 760pt；用户消息靠右、灰色圆角胶囊；回复无气泡。
  - 中间过程折叠为「用时 X ›」，展开后是说明文字夹着一行行灰色工具摘要（「运行了命令」等），再展开是带左侧竖线的命令列表；悬停文件改动弹出 diff 预览。
  - 文件改动卡片（「已编辑 文件 +N −N」与「查看变更」）；消息下方操作行（复制、更多）与时间；回到底部的圆形按钮。
  - 新会话空状态：居中图标与大标题「要在 *工作区* 里做什么？」，工作区名可点开切换。
- **输入框**：底部居中的圆角卡片。新会话时卡片上方是上下文条「主机 / 工作区 / 更多」，在这里选本机或某台远程主机；底部左侧 `+` 附件与审批模式菜单（图标、标题、说明、勾选，危险项用警示色），右侧模型与思考等级弹层（分档滑块）与圆形发送按钮（运行中变为停止）。
- **右侧面板**：标签页组织（「变更」，以后加文件、终端），`+` 打开带磁贴的新标签页；「变更」顶部是轮次范围选择（如「上一轮 +6 −1」），文件头显示路径与增删行数，统一 diff，未改动部分折叠；面板收起时右上角浮一张「更改：仓库 · 分支 +N −N」小卡。
- **弹层**：菜单、选择、审批模式、模型共用一种弹层外观，可带标题行与说明文字。

### 5.2 基础

N0 在任何页面之前完成，并在 N0 补充中按 5.1 调整：

- **`apps/desktop/DESIGN.md`**：视觉语言，字号与间距档位；密度（控件 32pt、行约 32pt、图标 14–16pt）；圆角、图标族、交互状态、支持的平台；每个页面的动效清单，写在该页面编码之前。
- **主题 token**：背景（应用底色、主区）、前景、次要文字、边框、强调、选中、焦点，以及成功、警告、危险、信息；分亮色和暗色两套；颜色值只出现在 token 定义里；用户设置的界面字体、代码字体、字重接入排版 token。
- **动效 token**：时长 `instant` 120ms、`fast` 180ms、`base` 240ms、`slow` 360ms；进入 ease-out，两处之间 ease-in-out，离开 ease-in；位移 4、8、16pt；按下缩放 0.95–0.97；减少动效时全部瞬时。
- **图标**：`ui` 的 `Icon`，背后是 Lucide SVG。文件图标在 N3 文件树时再定。不用字符或 emoji 当图标。
- **组件展示页**：列出每个 `ui` 组件的全部变体、尺寸、状态，分亮色和暗色。

`ui` 组件包装 `nsh/base` 中对应的组件；页面只用 `ui` 组件，不写颜色、圆角、字号，缺少的外观先在 `ui` 中加变体。

| 下拉菜单、选值 | `ui` 的 `Menu`（`Menu` 与 `Submenu`）、`Select` |

## 6. 状态与事件流

- **`src/client` 是纯 TS 状态机**：输入 ACP 帧，输出会话状态的变化；NSH 应用的 store 把它接到 signal。它不知道帧来自本机还是远程。
- **store**：都由 signal 组成，根组件创建，通过 context 下发；store 的方法是 signal 唯一的写入方。

| store | 持有 | 归属 |
| --- | --- | --- |
| `AppStore` | 主机列表（本机与远程主机）、当前主机与当前会话、导航历史（前进、后退）、`desktop.json` 设置、通知队列 | 根组件，全局唯一 |
| `HostStore` | 一个主机的传输与连接状态、会话目录、工作区、登录对话框队列（仅本机）、远程连接中的设备（仅本机） | `AppStore` 按主机 id 持有 |
| `SessionStore` | 一个会话的状态快照、行布局、每行的版本号、运行状态、控件选项、快照列表、消息标记，以及行回收后要保留的界面状态 | `HostStore` 按会话 id 持有 |
| `PanelStore` | 每个所有者的右侧面板：标签页、文件树、「改动」标签的范围与内容 | `HostStore` 按所有者 key 持有 |
| 组件内 signal | 悬停、草稿、菜单开合、编辑状态 | 组件自己 |

- **事件进界面**：传输层收到帧 → client 状态机 → store 更新 signal；结构变化才重建行布局，内容变化只给对应行的版本号加一；行版本号按行 id 存在 store 中；transcript 用 `List`，流式输出时只重绘变化的行。
- **持久化**：`desktop.json`（设置、远程主机列表）用 `fs/promises` 读写，防抖写盘；设备密钥与已信任设备由 `crates/remote` 存在应用数据目录（见 4.1）。
- **退出**：应用退出时同步等待本机后端停止（最多 10 s），关闭 iroh 端点；热更新或根组件销毁时在后台关闭。

## 7. 测试

- **`src/client`**：`nsh test` 运行 `*.test.ts`，覆盖状态机、解码、传输与连接，以及以后移植的轨迹、改动树等。
- **`crates/remote`**：`cargo test` 用本机上的两个 iroh 端点互连（不经公共 relay），覆盖：配对成功、过期或错误的一次性密钥被拒、连续错误后配对码作废、未信任设备被拒、协议版本不匹配被拒、撤销后立即断开、帧往返（含换行与非 ASCII）、主机专属能力被拒。
- **`crates/acp`、`ext/backend`**：`cargo test` 覆盖 `serve_lines`、后端启动与关闭、`Remote` 连接类型的拒绝规则。
- **NSH 应用**：`nsh test` 运行 `*.test.tsx`，在无界面模式下覆盖各功能流程；远程相关的界面测试同时覆盖本机与远程两种主机。
- **真实后端**：配置用 `apps/desktop/tests/fixture/config.toml`（`CLAW_CONFIG`）；不带它时连接真实后端的测试直接失败。
- **远程端到端**：R1 起，在同一台机器上运行两个应用实例（各自的数据目录），一个做主机、一个做遥控器，完成配对、远程对话、审批与撤销。
- **界面外观**：每个页面在亮色和暗色下截图（`nsh test --target linux`），跑完工检查清单并核对动效清单。

## 9. 可行性

N0 已验证的项见 `apps/desktop/FEASIBILITY.md`：引用应用目录外的代码（修订后不再需要）、扩展作为 workspace 成员、原生通道的高频帧、输入框（有条件通过）、几千行 transcript、1 MiB diff、树/分栏/剪贴板。

R1 计划开始前先验证（任何一项不通过就停下报告）：

1. iroh 1.5 能否在 `ext/backend` 中与 NSH 运行时、后端的 tokio 运行时共存，Linux 上构建与运行正常，macOS、Windows 可以构建。
2. 同一局域网与跨 NAT（经 n0 公共 relay）两种情况下，两台设备能连通，并测出首帧延迟与流式输出时的吞吐。
3. 二维码的生成与显示（Rust 生成 SVG 交给 `Image`，或 `ui` 组件绘制）。
4. 同一台机器上两个应用实例（各自数据目录）能同时运行、互相配对。

- 按设备分级权限、按会话授权。
- 修改或维护 WebUI；它的删除另行安排。
- 用 A2UI 渲染 agent 生成的界面。
- 为迁移修改 NSH 本身。
- 超出旧客户端大方向的新功能（远程控制除外）。
